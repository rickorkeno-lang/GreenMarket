# Карта и остальные правки Customer UI: что готово на бэкенде

Документ из двух частей. Первая — карта: контракт, по которому мок заменяется реальными данными. Вторая — остальные замечания из разбора Валентина от 09.08, которые закрываются на фронте; там же указано, что из них в этой сборке уже сделано, а что нет.

Экран карты сейчас работает на `MockSellerRepository` — и это не претензия: до сегодняшнего дня координат в системе не существовало, подключаться было не к чему. Теперь есть.

## Главное отличие от текущей модели

В моках координата принадлежит продавцу (`SellerMapRecord.location`). На бэкенде она принадлежит **месту торговли**, а продавец к нему привязан. Причина простая: на рынке торгуют сотни продавцов по одному адресу, и дублировать этот адрес в каждом профиле нельзя — он разъедется при первой же правке.

Мест торговли два типа, и на карте они ведут себя по-разному:

- `MARKET` — рынок. Один пин на всех его продавцов. Нажатие на пин → список продавцов рынка. У каждого есть ряд и место, по которым покупатель находит его внутри.
- `SHOP` — отдельно стоящая лавка в городе или деревне. Пин — это фактически сам продавец, ряда и места нет.

То есть пин на карте — это точка, а не продавец. Список продавцов приезжает вторым запросом, когда пин нажали.

## Эндпоинты

**Все точки для карты**

```
GET /api/v1/catalog/markets
```

```json
{
  "markets": [
    {
      "id": 1,
      "name": "Лавка у дома",
      "type": "SHOP",
      "address": "Казань, Баумана, 5",
      "latitude": "55.7900000",
      "longitude": "49.1200000",
      "seller_count": 1
    }
  ]
}
```

Координаты — строки (decimal, чтобы не терять точность при сериализации), перед передачей в карту нужен `Number()`.

Здесь координаты никогда не `null`: точка без координат на карту не ставится и в выдачу не попадает. Точка без единого видимого продавца тоже не отдаётся — пин, за которым пусто, хуже отсутствующего пина. Видимый продавец = активный и хотя бы с одним опубликованным товаром, то же правило, что в каталоге.

**Продавцы точки (содержимое пина)**

```
GET /api/v1/catalog/markets/{id}/sellers
```

```json
{
  "sellers": [
    {
      "seller_id": 3,
      "name": "Пасека Ромашково",
      "row": "Ряд 3",
      "place": "Место 12",
      "working_hours": "8:00–18:00",
      "short_description": null,
      "product_count": 12
    }
  ]
}
```

Сортировка по имени продавца. `row`/`place` пусты у лавки. Закрытая или несуществующая точка — `404` с телом `{"error": {"code": "NOT_FOUND", "message": "..."}}`.

**Карточка продавца (переход из списка)**

```
GET /api/v1/catalog/sellers/{id}
```

```json
{
  "seller_id": 3,
  "name": "Пасека Ромашково",
  "market": {
    "id": 1,
    "name": "Лавка у дома",
    "type": "SHOP",
    "address": "Казань, Баумана, 5",
    "latitude": "55.7900000",
    "longitude": "49.1200000"
  },
  "row": "Ряд 3",
  "place": "Место 12",
  "working_hours": "8:00–18:00",
  "short_description": null,
  "phone": "+7...",
  "whatsapp": null
}
```

Здесь, в отличие от списка точек, `market` может быть `null` (продавец не привязан к точке), а `latitude`/`longitude` внутри него — тоже `null` (точку завели по адресу, координаты не сняли). Оба состояния штатные, экран обязан их пережить: показывать адресом без пина.

## Чего в API нет и не будет к показу

Чтобы не ждать напрасно — этих полей из `SellerMapRecord` на бэкенде нет:

| Поле | Что с ним |
|---|---|
| `rating` | Отзывов в системе нет как сущности. Отдельная задача, не Stage 1 |
| `categories` / `categoryNames` | Товарные группы есть у товаров, у продавца — нет. Вывести можно, но нужен отдельный эндпоинт, скажите, если он нужен к показу |
| `photoUrl` | Фото есть у товаров, у продавца — нет. По нормативке отнесено к Stage 2 |
| `isOpenNow` | `working_hours` — свободный текст («8:00–18:00»), машинно не разбирается. Нужен структурированный формат, это отдельное решение |
| `distanceMeters` | Считается на клиенте от точки пользователя, бэкенд для этого не нужен |

Предлагаю на показ строить карту на том, что есть: пины точек, список продавцов внутри, переход в карточку продавца и его товары.

## Остальные замечания Валентина по Customer UI

Разбор от 09.08 делался по сборке, задеплоенной на `green-market-nine.vercel.app`. Мы посмотрели код этой сборки — часть замечаний в ней уже неактуальна, и переделывать ничего не нужно.

**1. Разнокалиберные фото в сетке каталога — уже закрыто.** В `buyer_mvp.css` плитка описана правильно:

```css
.gm-buyer-photo {
  width: 100%;
  aspect-ratio: 1 / 1;
  object-fit: cover;
}
```

API отдаёт ссылки на оригиналы, пропорции у продавцов разные, и именно этот CSS их выравнивает. Отдельной задачи здесь нет.

**2. Фильтр по товарным группам — работает, но не там, где его искали.** Дерево категорий живёт на главной: выбор категории уводит в `/catalog?group_id=N`, каталог фильтрацию поддерживает. Но из самого каталога переключить категорию нельзя — есть только «Сбросить категорию», а для выбора другой надо вернуться на главную. Валентин смотрел именно каталог, поэтому и написал «фильтр забыт».

Просьба: вывести категории прямо над сеткой каталога, рядом с «По названию / По цене». Данные те же:

- `GET /api/v1/catalog/groups` → `{"groups": [{"id", "parent_id", "name", "sort_order", "product_count"}]}`
- `GET /api/v1/catalog/products?group_id=<id>`

Для Stage 1 хватит плоского ряда чипов; `parent_id` нужен, только если захочется дерева.

**3. Полноэкранный просмотр фото — этого нет.** `PhotoStrip` переключает активное фото, но открыть его крупно нельзя. Валентин спрашивал, как посмотреть дополнительные фото, — миниатюры он нашёл, а увеличить не смог. Нужен лайтбокс.

**4. Новые поля карточки товара — их сейчас нет в типах.** `buyer_mvp/types.ts` описывает контракт до сегодняшних изменений. Обновить нужно так:

```ts
export interface SellerOffer {
  // ...существующие поля
  origin_country: string | null;
  supply_date: string | null;   // "ГГГГ-ММ-ДД"
}

export interface ProductDetail {
  id: number;
  name: string;
  description: string | null;
  group_id: number;
  group_name: string;
  offers: SellerOffer[];
}
```

`group_name` — товарная группа, её просил показать Валентин. `origin_country` и `supply_date` относятся к предложению конкретного продавца, а не к товару: один и тот же авокадо у одного продавца из Перу и привезён вчера, у другого из Кении и лежит третий день. Оба поля могут быть `null` — колонки в книге продавца необязательные; строку выводить только когда значение есть.

Про `supply_date`: дата трактуется относительно сегодняшнего дня. Прошедшая — состоявшийся завоз, признак свежести («привезено 01.08»); будущая — планируемая поставка («ожидается 12.08»). Сервер её не размечает, сравнение с текущей датой — на стороне UI.

Вызова карточки продавца в `api.ts` нет вовсе — его нужно добавить, он же понадобится карте (см. первую часть).

## Адрес API

Рабочий адрес — `https://testapi.vnespecplanpodaz.online`, базовый путь каталога `/api/v1/catalog`.

В репозитории сейчас `vite.config.ts` проксирует на `http://104.171.133.95` с комментарием «CORS пока не решён на бэке» — это устарело: CORS настроен 29 июля, домен с HTTPS поднят 30 июля. Прокси для локальной разработки можно оставить, но цель лучше поменять на домен, а для сборки задать `VITE_API_BASE`.

**Что нужно от вас:** адрес, по которому деплоится фронт. CORS у нас разрешает конкретный список источников; если фронт живёт по другому адресу, браузер срежет запросы, и выглядеть это будет как «бэкенд не отвечает». Правка на нашей стороне минутная, но нужен адрес.
